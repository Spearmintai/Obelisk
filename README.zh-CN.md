## 一、问题

两台机器各敲一行同样的命令。同一个随机种子，同一份代码，同一个 PyTorch 版本。

| | 英伟达 RTX 4090 | 摩尔线程 MTT S4000 |
|---|---|---|
| `rand`（均匀分布） | +0.51667917 | +0.51667917 |
| `randn`（正态分布） | −0.42534423 | −0.4253**4396** |
| `log1p` | +0.69314718 | `NotImplementedError` |

均匀分布的随机流逐位相同，说明随机数发生器移植是对的。往下的每一步就不是了。

还有更要命的一个，因为它什么都不破坏。`SELU` 是标准激活函数，对正数要乘 1.0507。

| 由谁计算 | 结果 | 误差 |
|---|---|---|
| 闭式定义，float64 | 3.216856 | — |
| CPU | 3.216856 | 1.2e−07 |
| RTX 4090 | 3.216856 | 1.2e−07 |
| **MTT S4000** | **3.061628** | **4.8e−02** |

不抛异常，不打警告，不降级。用 SELU 的模型会在这张卡上正常训练、画出 loss 曲线、收敛，然后每一个正激活都低五个百分点。

这就是整个行业没有在量的那道缝。解决"能不能跑"的工具很多，回答"跑得对不对"的一个也没有。而一笔上亿的算力采购，签字的人要的恰恰是后面那个答案。

## 二、产品

三个问题，需要的访问权限一层比一层少。

| 问题 | 需要什么 | 大小 | 给谁 |
|---|---|---|---|
| **能不能跑** | 算子与数据类型支持表 | 3 KB | 可公开 |
| **跑得对不对** | 数值指纹 | 562 KB | 买方 |
| **实际跑了什么** | 替换账本 | 运行时产生 | 使用者 |

方法建立在四个判断上。

- **CPU 是"这个调用合不合法"的裁判，设备是被测对象。** 每个用例先在 CPU 上跑一遍，CPU 不认的算我们自己写错了，直接丢弃，不算在卡头上。
- **一份指纹等于摘要加 float64 统计量加 512 个确定性采样。** 小到能放进文本文件带走，又足以在两个张量都不在场的情况下逐点比对。
- **误差按张量自身的尺度衡量**，不按逐元素相对值。两个 1e-41 相差 1e-41 是"相差百分之百"，可它们都是零。
- **没有理由不同的量，要求逐位相同**：随机流、排序顺序。算术只要求足够接近。

```
obe sample     打印几个数，在两台机器上各跑一次，并排读
obe dump       完整测量一台设备：所有算子、所有数据类型、15 个假设探针
obe diff       比对两份画像，不需要任何硬件在场
obe cards      这份安装里已经认识哪些设备
obe check      用别处测过的卡，审判这里的代码仓库
obe run        把缺口补上把程序跑完，并交代每一次替换
obe record     为某个负载测量基准
obe verify     用记录下来的基准核验当前设备
obe inspect    在还没有卡的时候，从源码预判风险
obe migrate    改写到另一个后端，并报告它改不动的地方
```

## 三、演示

**三十秒版。** 两台机器各敲一行，然后并排读两段输出。

```
obe sample
```

**完整版：卡和代码从不见面。** 这才是这件事真实的样子——代码在笔记本上，卡在机房里没有外网，而且没人把代码送进去过。

```
# 在卡上，你的代码一行都不需要在场
obe dump --out s4000.obl

# 一个文件，不到一兆，用机房允许的任何方式带出来
scp s4000.obl laptop:

# 在一台没有显卡、连 PyTorch 都没装的机器上
obe check ./your-repo --card s4000.obl
```

```
  CODE AGAINST CARD                                              GRADE  C

  7 个算子确定、1 个大概率会在这里失败，而且每一个都能被替换。

   x  torch.slogdet    4 处调用   normflows/flows/mixing.py:117
   x  torch.std        3 处调用   normflows/flows/normalization.py:23
   x  F.logsigmoid     2 处调用   normflows/transforms.py:29
   x  torch.qr         2 处调用   normflows/flows/mixing.py:73
```

没人买卡，没人把代码送进机房，没人排队等机位。

**然后让它真的跑起来，并且交代代价。**

```
obe run train.py
```

缺算子通常不是缺能力。`log1p` 就是 `log(1+x)`，标准差就是方差开根号。Obelisk 用三种方式补，并且每一次都记账：用这张卡有的算子**重写**、送回 **CPU** 计算、或者因为设备自己的内核是错的而**纠正**它。

```
  账本：哪些事情没有按你写的方式发生

   算子          方式         调用次数   秒      精度
   selu          纠正             2     0.000   精确
   slogdet       CPU 兜底         1     0.001   精确
   std           重写             1     0.000   精确
   log1p         CPU 兜底         1     0.008   3.1e-01

   selu 被调用了 2 次；设备内核是错的，所以你拿到的结果
   不是这张卡会给你的结果
```

重点不是程序不再崩溃。让程序不崩溃谁都会。重点是最后那一句，一个沉默的兼容层永远不会告诉你。

## 四、验证

2026 年 10 月 12 日实测，两台租用的机器，两边都是 PyTorch 2.2.0，这样框架版本不构成差异的来源。

**算子覆盖。** 用内省发现七百个可调用接口，其中 399 个被 CPU 认可，在两张卡上各跑一遍。

| | RTX 4090 | MTT S4000 |
|---|---|---|
| 行为一致 | 386 | 272 |
| 结果不同 | 10 | 20 |
| **根本不存在** | **1** | **73 个不同的运算** |

国产卡上缺失的包括：`std`、`median`、`svd`、`qr`、`cholesky`、`det`、`logdet`、`slogdet`、`lu`、`triangular_solve`、`cdist`、`pdist`、`asin`、`asinh`、`acosh`、`atanh`、`sinh`、`cosh`、`log1p`、`exp2`、`erfc`、`lgamma`、`digamma`、`i0`、`nansum`、`nanmean`、`kthvalue`、`logaddexp`、`logsigmoid`、`mish`。

**沉默地算错。** `SELU` 低 5%。`torch.log` 在 1+2⁻²³ 处错 30.7%，在 1+2⁻²⁰ 处错 4.0%，而在 1.5 处精确到 2.9e−08，这会污染任何落在 1 附近的对数似然。`vander` 错 100%。`max_pool1d_with_indices` 返回的形状不对。

**数据类型。** float64 能分配、能求和，但不能做加法和矩阵乘。complex64 连分配都不行。

**假设。** 15 个探针里有 3 个超出容差：半精度累加器宽度 3.37e−04、layer_norm 的 epsilon 1.32e−05、scatter-add 的累加顺序 4.33e−03。两个本该逐位相同的量并不相同：随机流（均匀分布逐位相同，到正态分布的变换不同），以及 sort、topk、argmax 的并列处理。

**一个对这张卡有利的测量。** float32 矩阵乘的有效尾数是 20.0 位，4090 是 21.7 位，两者都对照同一个在 CPU 上用 float64 精确算出的乘积。如果真的偷偷缩短了 float32，这个数会是 11。两张卡都没有作弊，而且这个结论任何人都能照着重做一遍。

**以及那个诚实的反面结果，它才是让前面所有数字可信的东西。** 一个四层 transformer 在两张卡上用完全相同的权重和批次跑：28 层里 28 层都在容差内，50 步训练之后 loss 相差 3.73e−09，参数相差 5.36e−09。这个负载恰好一个坏掉的部件都没碰到。它在这张卡上是好的。说清楚哪些负载受影响、哪些不受影响，才是这件事的全部工作；一份只会说"不行"的报告不值得读。

**我们用同样的标准审了自己的工具。** 第一版替换实现犯了跟被测卡一模一样的错：`log(1+x)` 对小 x 返回 0，所以我们的 `log1p` 错了 100%，而且一声不吭。现在它们按库级的稳定写法重写，并且每个替换在启动时都拿 float64 的结果测量自己，误差超过 1e−4 就拒绝安装。这条规则立刻证明了自己的价值：修正后的 `log1p` 在 S4000 上仍然测出 3.1e−01，而同一段代码在 CPU 上是 1.2e−07，在 4090 上与 CPU 逐位相同。公式是对的，是这张卡的对数函数不对。上面那个 `log` 缺陷就是这样被找出来的。

## 五、现状

- **已在 PyPI。** `pip install obelisk-env`，装进空环境即可用，零依赖。
- **七个真实仓库测过**，包括 2125 个 Python 文件的 diffusers，在没有显卡也没有 PyTorch 的机器上约一秒读完。
- **卡库里已有两台设备**，随包分发，所以 `obe check ./repo --card mtt-s4000-musa` 连文件都不需要。
- **三台机器的工作流已端到端跑通**：卡单独测量，文件带走，结论在一台没有显卡的机器上产出。

### 边界

这里所有的测量都只针对一张摩尔线程 MTT S4000，驱动 2.7.0，torch 2.2.0。昇腾、寒武纪、天数智芯的卡一张都没有测过。一张卡的画像只对它被测量时的那个配置成立，所以每张能力卡都记录了驱动和框架版本，`obe check` 会把它打出来。一张过期的卡比没有卡更糟，因为它会被相信。
